# Contributing to autocto

## Running tests

```bash
pip install -e ".[dev]"
pytest tests/ -q
```

Tests need Python 3.12+ (matches `pyproject.toml`'s `requires-python` and the
CI workflow) and no network access or API keys - every analyzer is pure
git-log/file-tokenizing logic.

## The pattern this repo follows

Every analyzer module is split into two layers:

1. **Pure functions** - take plain data in (strings, dicts, sets), return
   plain data out. No filesystem, no subprocess, no I/O. These are the
   functions unit tests exercise directly with fixture strings (see
   `parse_numstat_log`, `complexity_score`, `compute_hotspots` in
   `src/autocto/hotspots.py`, or `tokenize`, `shingle`, `jaccard_similarity`,
   `find_duplicates` in `src/autocto/duplicates.py`).
2. **One effectful entry point per module**, `analyze_repo(repo_dir, ...)`,
   which does the real filesystem/subprocess work and calls the pure
   functions to do the actual scoring. Where a module needs a genuinely
   effectful operation (hotspots.py's `git log` subprocess call), that
   operation is an injectable callable with a real default (`git_log_fn`),
   the same dependency-injection pattern used elsewhere in the
   ai-ecosystem (e.g. `second_brain.vault.ingest_vault`'s `ingest_fn`). This
   lets `analyze_repo`'s own tests supply a fixture instead of mocking
   subprocess internals, while still having an end-to-end test that exercises
   a real repo (see `test_analyze_repo_end_to_end_against_a_real_git_repo`
   and `test_analyze_repo_accepts_an_injected_git_log_fn` in
   `tests/test_hotspots.py`).

New analyzers should follow the same split: pure scoring logic first, one
effectful `analyze_repo` wiring function last, any unavoidable I/O behind an
injectable callable with a real default.

## House rules

- Never use the em dash character (U+2014) anywhere; use " - " instead. In
  tests that must reference the character itself, use `chr(0x2014)`, not the
  literal.
- Never add Claude/Anthropic attribution anywhere: no `Co-Authored-By:
  Claude` trailer, no "Generated by Claude Code" / "Generated with Claude
  Code" footer, on any commit, PR description, or PR comment.
- No dead code, no commented-out blocks, no TODOs without an issue reference.

## PR expectations

- Keep changes scoped to one analyzer or one concern per PR.
- New analyzer logic needs tests covering the pure functions directly, plus
  at least one `analyze_repo` end-to-end test against a real fixture (a real
  temp git repo for hotspots-style modules, a real temp directory tree for
  duplicates-style modules).
- Run `pytest tests/ -q` locally and confirm it is green before opening the
  PR; CI (`.github/workflows/ci.yml`) runs the same command on every push and
  pull request against `main`.
- This repo does analysis only - it must not grow a code-writing or
  PR-opening path of its own. That belongs to the separate `/github-pr`
  skill in the `github-pr-agent` project.
